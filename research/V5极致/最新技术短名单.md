# VoiceTwin + GPT-SoVITS V5：最新技术短名单（截至 2026-11-24，合并三份调研）

**标注说明**
- **[摘要]/[片段]**：数字来自论文摘要或搜索摘录。本次 arxiv.org 和 huggingface.co 访问不了，全文没有读到。

## 0. 先核实的本地事实（会改变排序）
- **显卡**：老师的电脑是 **RTX 5070 Laptop，8 GB 显存，空闲约 6.8 GB**，PyTorch 2.7.0+cu128（教学手册.md 第 188 行，已核）。推理时要 7 GB 以上的模型，以及几乎所有 2B 以上模型的微调，本机都跑不了。
- **已有的备选引擎**：Qwen3-TTS 和 IndexTTS 2.5 已经接进程序，做零样本备选（教学手册.md 第 63 行，已核）。
- **混用引擎的已知问题**：同一篇里混用不同频宽，会听出"忽亮忽暗"，打分（16 kHz）却看不出来（research/一模一样/记录.md 第 106 行，已核）。
- **默认打分模型**：`DEFAULT_ENSEMBLE = ReDimNet2-B6、ERes2NetV2-zh、ERes2Net-base-zh`，都是 16 kHz。CAM++ zh-en 只是备选（voicetwin/eval/sv_models.py，已核）。
- **V5 的推理参数**：VoiceTwin 发给 api_v2 的请求里**没有 cfg_rate**；`sample_steps` 是 auto，也就是官方默认（v5dev 32 步）；`super_sampling=False`（voicetwin/backends/gptsovits.py 约 3910–3936 行，已核）。所以 CFG 现在用的是官方默认 1.30（[代码] TTS_infer_pack/TTS.py）。

## 1. 值得配合 V5 试的模型和工具

### A. 生成模型（拿来做对照或辅助，不替换 V5）

**1. dots.tts（SOAR 或 MF）+ dots.tts.edit**（rednote-hilab，https://github.com/rednote-hilab/dots.tts）
- **角色**：
  - 作为整篇的备选引擎或对照基准。
  - 给纯英文句子当"第二意见"。
  - 用 edit 修好句子里个别读错的词（尤其英文词），不必整句重生成。
- **证据**（README）：
  - 发布于 2026.06，edit v1.1 于 2026.10。
  - Seed-TTS-eval 零样本 SIM：zh / en / zh-hard 为 81.0 / 77.1 / 79.5（SOAR），MF 4 步 80.0 / 76.2。
  - CV3 跨语言 SIM：en→zh 75.0，zh→en 72.8。
  - 48 kHz，和 V5 频宽相同。
  - dots.tts.edit **没有公布任何分数**。
- **许可**：Apache-2.0（写着 "research and authorized deployment"）。
- **能不能在 Windows + 8 GB 上跑**：
  - H800 上实测峰值：MF 5.74 GB，SOAR 7.86 GB（≤256 patches）。所以 MF 可能放得下，但不能和 GPT-SoVITS 同时占显卡，要轮流用。
  - README 没提 Windows；第三方说只支持 Linux/macOS，要走 WSL2 [未核实]。
- **微调**：有训练脚本 `scripts/train_dots_tts.py`，但没有单人、LoRA 或硬件方面的说明。
- **工作量**：中到高。
- **注意**：
  - 同是 48 kHz，但换引擎后音色是否一致还没测过。
  - edit 修词后，没改的部分是否保持原样，也需要先验证 [未核实]。

**2. VoxCPM2**（OpenBMB，https://github.com/OpenBMB/VoxCPM）
- **角色**：在老师自己留出的真录音上，做"微调对微调"的公平对照。它是唯一一个有官方单人 LoRA 文档的一线模型。
- **证据**：
  - 发布于 2026.04。零样本 SIM zh / en 79.5 / 75.3。2B，48 kHz。
  - 官方 LoRA 和全量微调，带 LoRA 网页界面。文档说 5–50 条音频、1–3 个 epoch；LoRA 约 20 GB、全量约 40 GB（batch 16）[片段，来自 readthedocs，本次打不开]。
- **许可**：Apache-2.0，写明可商用。
- **能不能在 Windows + 8 GB 上跑**：
  - 推理约 8 GB（4090 上 RTF 0.30），本机处在边缘。
  - LoRA 用 batch 1 能否在 8 GB 跑起来 [未核实]。
  - 官方没提 Windows，只有社区整合包。
- **工作量**：高。

**3. LongCat-AudioDiT 1B（本机）/ 3.5B（fp8 或云端）**（美团，https://github.com/meituan-longcat/LongCat-AudioDiT，MIT）
- **角色**：零样本"天花板"对照，也可当英文的第二意见。如果微调后的 V5 在留出句上比不过它，说明训练还有问题。
- **证据**：
  - 3.5B 零样本 SIM zh / en 0.818 / 0.786，是目前查到的最高公开值；1B 为 0.812 / 0.762。
  - 显存是第三方数字 [未核实]：1B 约 4 GB（bf16），3.5B 约 9 GB（bf16）。
- **限制**：
  - 输出 24 kHz，**绝不能和 48 kHz 的 V5 按句混用**。
  - 没有微调代码。
  - Windows 支持没写。
- **工作量**：中。

**4. FireRedTTS3**（https://github.com/FireRedTeam/FireRedTTS3）
- **角色**：只做研究对照。
- **证据**：SIM 80.9 / 77.2 / 78.4。
- **为什么排低**：
  - LICENSE 是 Apache-2.0，但 README 说零样本克隆"solely for academic research"。
  - 没公布模型大小、显存和微调信息。

**5. Qwen3-TTS 单人微调**（已接入的引擎；https://github.com/QwenLM/Qwen3-TTS/tree/main/finetuning）
- **角色**：低优先级对照。
- **证据**：有 1.7B-Base 的单人 SFT 脚本，但没有显存和数据量说明。在 8 GB 上能否微调 [未核实]。

**6. GLM-TTS**（https://github.com/zai-org/GLM-TTS，Apache-2.0）
- **角色**：不建议当引擎用，主要价值是它的 GRPO 代码，可作策略 C2 的参考实现。
- **证据**：报告声称 LoRA 用 1 小时单人数据就能达到全量微调水平 [未核实]。

### B. 变声（VC）：只能当"孪生候选"，交给现有的逐句挑选器，不能做强制步骤

**7. RVC 48k，用 Applio 3.7.2**（2026-11-19；https://github.com/IAHispano/Applio）
- **许可**：MIT。
- **Windows**：`run-install.bat` 装的是 cu128，RTX 50 可用（已在仓库核实）。
- **做法**：音高（f0）取自 V5 的输出（RMVPE），检索库用老师自己的录音。
- **证据**：**没有公开的语音相似度、MOS 或 WER 数字**；Applio 也说现在不常更新。
- **工作量**：中。

**8. Seed-VC v1 44.1 kHz f0 条件版，用老师的数据微调**（https://github.com/Plachtaa/seed-vc）
- **许可和状态**：GPL-3.0，只能作为独立工具运行；仓库已于 2025-11-21 归档，不会再修 bug。
- **证据**（EVAL.md，用的是较弱的 Resemblyzer 打分）：
  - 零样本 SECS 0.8676，但 CER 从真人的 1.57 升到 2.92。
  - README 说微调能"largely improve"相似度，但没有数字。
- **Windows / RTX 50**：requirements 固定 torch==2.4.0，RTX 50 要换 cu128 版 torch [未核实]。
- **评分注意**：它内部用的是 CAM++，所以给它的候选打分时不能用 CAM++。
- **工作量**：中到高。

### C. 评测和把关工具
- **TTSDS2**（`pip install ttsds`，MIT，ICLR 2026）
  - 用途：拿生成的整篇课和老师的真录音，按韵律、音色、清晰度逐项比，用来调参数，不用来挑句子。
  - 证据：16 个指标里，只有它在所有领域和人工打分的相关都超过 0.5 [摘要]。
  - 限制：Windows 支持 [未核实]，依赖 apt 和 fairseq，很可能要 WSL。
- **审计用的声纹模型**：不参与挑选，只用来查账。
  - 候选：程序里已有的 CAM++ zh-en 备选，或 Seed-TTS-eval 用的 WavLM-large SV。
  - 例外：审计 Seed-VC 候选时不能用 CAM++。
- **SpeechJudge-GRM**（https://github.com/AmphionTeam/SpeechJudge）
  - 用途：两句分数难分高下时，做最后的二选一。
  - 证据：和人工 A/B 选择一致 77.2%，推理时多次采样后 79.4% [摘要]。
  - 限制：
    - 基于 Qwen2.5-Omni-7B，bf16 光权重就约 14 GB 以上 [估计]，**8 GB 本机放不下**。
    - 许可没写（仓库根目录没有 LICENSE）。
    - 中文支持 [未核实]。
  - 结论：暂缓。
- **CrisperWhisper 2.0**（逐字转写）
  - 限制：只许非商业使用；中文支持 [未核实]；87.8 的 F1 是厂商自报。
  - 替代办法：用程序里已有的两个 ASR 引擎互相对比，标出不一致的片段。

## 2. 应该采用的策略（按"预期收益 ÷ 工作量"排序）

先说验收：每一项都在现有留出集上 A/B（20 条验证音频 + 24 条测试文本）。**同时满足**以下条件才保留：
- "像你本人%"上升；
- CER 不变差；
- 韵律分布离她的真录音不变远；
- 审计声纹模型同方向变化。

1. **加审计声纹模型，防"打分作弊"**（A4）。工作量低。
   - 依据：在扩散超分辨率任务上，候选超过约 2^3–2^4 个后，声纹类评判器收益递减甚至变负 [摘要，arXiv 2508.02391，是别的任务]；LLM 的 best-of-N 也有同样现象 [arXiv 2404.01054]。
   - 做法：逐句记录"审计分随候选数 N 的变化"。如果在 N≈8–16 就平了，候选上限就定在那里，还能省时间。
2. **在老师的 LoRA 上扫 cfg_rate**（A1）。工作量低。
   - api_v2 本来就收这个参数，不用改代码；现在程序没发，等于用默认 1.30（已核）。
   - 扫描值：0 / 0.7 / 1.0 / 1.3 / 1.6 / 2.0 / 2.5。
   - 依据：
     - Koel-TTS（arXiv 2502.05236）：CFG 加大，CER 降、SSIM 升 [摘要]。
     - Align2Speak 重跑 Koel：CER 从 2.68% 降到 0.57% [摘要]。
     - BareWave（arXiv 2606.09048）：SIM 在 CFG 3.5 时最高，之后下降 [摘要]。
   - 为什么 1.30 未必对她最好：V5 的 LoRA 微调没有条件 dropout（[代码] dit.py 里标着 "###no-use"），1.30 是为底模调的 [未核实，推断]。
3. **试 32 步和 64 步，以及 cache-dit**（A6）。工作量低。
   - 推断 2 的幂次步数（8/16/32/64）是训练时见过的步长 [代码推断]。
   - cache-dit 默认关闭，代码注释说"near-identical audio"，能换来更多候选。
   - 按审计分来定，不按挑选分。
4. **guidance interval：只在部分步数上用 CFG**（A2）。工作量低，monkeypatch 约 3 行，还能省算力。
   - 依据：
     - Kynkäänniemi et al., NeurIPS 2024（arXiv 2404.07724）：高噪声阶段的 guidance 有害，中段有益 [摘要]。
     - arXiv 2611.11179（2026 年 11 月）：在同类的 token 条件流匹配 TTS 上，2 步时给第一步（纯噪声）加 guidance，会损失 1–6 个 SIM 点 [摘要]。
   - 扫描值：t0 ∈ {0, 0.1, 0.2, 0.3}。
   - 如果以后要用 v5turbo（4 步），这一项更重要。
5. **停顿长度跟下一句的长度挂钩**（D1）。工作量低到中。
   - 现状：`_twin_pause` 在 u∈[0.2, 0.8] 内独立抽样，和上下文无关（engine.py:2646）。
   - 依据：Krivokapić 2007 和 Fuchs et al. 2013（J. Phonetics）发现，停顿随后面短语或句子的长度变化。
   - 前提：先在她的录音上拟合，斜率显著才用。
   - 句间仍然保持绝对数字静音。
6. **清理转写（训练一次）**（B1/B2）。工作量中。
   - 依据：Whisper 系 ASR 会漏掉口头填充词和改口 [arXiv 2408.16589，摘要]。
   - 做法：
     - 转写按她实际说的写，**不要往稿子里加填充词**（Matsunaga et al. 发现加了可能更不自然 [摘要]）。
     - 用 GPT 阶段每条真录音的 NLL 找离群样本，复核或剔除 [未核实的改造，类比 Self-Purifying Flow Matching，arXiv 2509.19091]。
7. **autoguidance：用早期或低秩的 LoRA 当"弱模型"**（A3）。工作量中，要改代码：挂第二个 peft adapter。
   - 依据：VoiceGuider（arXiv 2409.15759）用这招让 LoRA 自适应模型达到全量微调的 SECS；对全量微调模型帮助很小 [摘要]。
   - 风险：V5 加 2.5 小时数据的域内微调效果未知 [未核实]。
8. **段落级韵律衔接**（D2）。工作量中，要改代码。
   - 做法：GPT 的 prompt 用上一句已选中的输出，CFM 的 mel prompt 仍用她的真参考 [未核实]。
   - 依据：有界的前文条件有帮助 [arXiv 2603.06444 等，摘要]。
   - 程序已有的整篇连贯重选覆盖了一部分。
9. **GPT 阶段做 SpeechAlign 式 DPO**（C1）。工作量高。
   - 做法：chosen 用她的真 semantic token，rejected 用模型自己的采样。
   - GPT-SoVITS 现成的 `dpo_loss` 能用 [代码]，只需替换 `make_reject_y`。
   - 依据：SpeechAlign（arXiv 2404.05600）优于 SFT [摘要]。反面见第 4 节。
10. **用已打分的候选当奖励**（C2）。工作量高，估计要几天工程。
    - 两种做法：Koel 式 DPO 对；或 GROW 式按奖励加权的流匹配 LoRA 训练（arXiv 2608.03215）[摘要]。
    - 预期收益：主要是失败少了，SIM 提升小。GLM-TTS GRPO 的 SIM 从 76.1 到 76.4 [代码 README]。
    - **必须加韵律分布约束**：arXiv 2509.18531 发现会把韵律压平 [摘要]。
11. **低优先级**：
    - B3 质量过滤：只剔明显离群的片段。
    - C3 LoRA rank 64/128 或全量微调：VoiceTailor 发现 rank 2 已接近够用 [摘要]。
    - 给 LoRA 加 F5 式条件 dropout：只在 A1 显示 CFG 行为异常时才试。
12. **两个 VC 孪生候选**（RVC、Seed-VC）。只做一轮 A/B：留出集声纹分上升、CER 不升、老师 ABX 不偏向原版 V5，三条同时满足才保留，否则放弃。

**最后验收"听不出来"（必做）**：
- 盲听：用老师留出的真句子，和同文本的生成版对比，包括 30–60 秒的整段；听众要是熟悉她声音的人；准确率和 50% 没有显著差别才算过。
- 可参照的人类基准：ElevenLabs 克隆约 60% 能被识破（Barrington et al., Sci. Rep. 2025）；San Segundo et al. 为 59.11%（arXiv 2512.09221）。

## 3. 看起来热门、但证据不足的东西
- **"SIM 高于真人就等于听不出来"**：不成立。
  - 真人基准只有 zh 0.755 / en 0.734，而 v5dev 是 0.805、LongCat 是 0.818。超过真人只说明模型复制了参考音频的录音条件。
  - 零样本 SIM 也预测不了微调后的排名。
  - DMOSpeech：逐句 WavLM-SIM 和人工 SMOS 的相关只有 r≈0.5 [摘要]。
- **v5pro 0.824**：官方还没发布。
- **Fish S2-Pro 的 Audio Turing Test 0.515**：自报，量表含义没核实。
- **Fish Drama 3**：要 48 GB 显存，是二手来源。
- **Breeze TTS 2 "开源权重第一"**：厂商自称，而且权重非商用。
- **VoxMel / Audio8 / Reverb-TTS**：只出现在 tts-bench 一个来源里，找不到一手资料。
- **"TTS 后接 VC 能提升相似度"**：
  - 没有任何 GPT-SoVITS→RVC/Seed-VC 的公开 A/B。
  - Voice Filter 的 MUSHRA 相似度 70.38，低于微调 TTS 的 73.67 [片段]。
- **换声码器（BigVGAN-v2 / Vocos）、频宽扩展（AP-BWE / MossFormer2_SR）**：V5 已经是 48 kHz，自带新声码器，没有证据说换了有用；而且 16 kHz 的打分看不到 8 kHz 以上的部分。
- **语音增强做后处理（Sidon / ClearerVoice / Resemble Enhance）**：会改变音色或内容（TIMUSE、PASE [片段]）。
- **用 UTMOS/UTMOSv2/DNSMOS 在系统内部给候选排序**：
  - TTSDS2 里 UTMOS 的平均 Spearman 约 -0.04 [摘要]。
  - UTMOSv2 多次运行结果不稳定 [摘要]。
- **"RL/GRPO 能大幅提升像不像"**：零样本 SIM 只提升约 0.3–2.3 点；好几篇报告韵律变平或 SIM 不稳。
- **Selective CFG（强调说话人的 guidance）**：在中文 F5-TTS 上无效 [摘要]。
- **sway sampling**：V5 有步长嵌入，没测过。
- **PCI、F5R-TTS GRPO**：机制上不适用于 V5 [代码]。
- **dots.tts.edit 修词**：没有公开评测。
- **"数字静音会暴露 AI"**：没有证据。已知的检测线索是首尾静音**时长**的分布（Müller et al. 2021 [摘要]），不是静音为零本身。

## 4. 证据互相矛盾的地方
1. **显卡**：任务说的是笼统的 "RTX 50 系"，本地手册写的是 **5070 Laptop 8 GB**（已核）。所有显存判断都按 8 GB 来。
2. **打分模型**：VC 调研写的是"ERes2NetV2 + CAM++ + ReDimNet2"，实际代码默认是 ReDimNet2-B6 + ERes2NetV2 + ERes2Net-base，CAM++ 只是备选（已核）。
   - 结果一：Seed-VC 内部的 CAM++ 不直接"刷"默认打分，但 CAM++ 不能当它的审计模型。
   - 结果二：X-VC 用的 ERes2Net 和三个默认打分模型里的两个同族（反正因为 16 kHz 已经排除）。
3. **FireRedTTS3 的许可**：LICENSE 是 Apache-2.0，README 却限定零样本克隆只能用于学术研究。
4. **dots.tts 的 Windows 支持**：官方没提，第三方说只支持 Linux/macOS [未核实]。
5. **VC 微调**：Seed-VC README 说微调"大幅提升"相似度（无数字）；但 Voice Filter 显示微调 TTS 更好，arXiv 2610.29351 显示级联方案的词错误更多。
6. **CFG 强度**：Koel 说越大越好；BareWave 说 3.5 之后下降；Selective CFG 在中文上无效。V5 的 1.30 是为底模定的。
7. **DPO**：SpeechAlign 优于 SFT；但 arXiv 2606.18323 发现离线 DPO/IPO 不如直接蒸馏 best-of-N 的结果；CosyVoice 2 的 DPO 损害了难句（据 arXiv 2509.18569 的转述）；GPT-SoVITS 自带的 DPO 只用来治重复和漏字。
8. **GRPO 用 SIM 当奖励**：GLM-TTS 在用；arXiv 2509.18531 却发现加 SIM 奖励会让训练不稳。
9. **客观指标和人耳**：kNN-TTS 客观 SIM 最高，听众却更喜欢 HierSpeech++ [片段]。
10. **呼吸声**：有证据说加了更自然（arXiv 2402.00288，40 人 MOS [摘要]），但和老师"句间绝对静音"的硬规矩冲突。只有她的录音本身有起句呼吸、并且经她同意，才考虑。
11. **用 GitHub Actions 的 GPU 训练**：
    - larger runner 是 T4 16 GB，只有 Team/Enterprise 方案才有，而 VoxCPM2 LoRA 官方要约 20 GB（batch 16）。
    - 更要紧的是，仓库约定"公开仓库不放老师录音和模型"。拿她的录音上 GitHub Actions 训练，要私有仓库或别的方案，还要老师同意。
12. **混用引擎**：本地已证实 48/32 kHz 混用会忽亮忽暗。dots.tts 同为 48 kHz，但跨引擎音色是否一致没验证。LongCat（24 kHz）和 V5 按句混用一定不行。
13. **显存数字的来源**：dots.tts 的显存是 H800 上测的，LongCat 的是第三方数字，在 5070 Laptop 上会不会一样都 [未核实]。另外，RVC "时间轴不变"是 RVC 的一般行为，Applio 代码里没有核实。
